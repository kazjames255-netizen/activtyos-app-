# Learning Hub — contract (tutoring vertical)

Student-facing hub for tutoring providers (1:1 / small-group). Freelancers, company
owners, franchises and **staff** author and run it; a **parent** uses it for their
enrolled child (the child is the "student"). Backend is built in-house (not Amir).
`server/openapi.yaml` (tag `learning-hub`) is the API reference; **this file is the
design contract**: schemas, rules, and request/response shapes both sides code to.

Hard rules: every doc carries `tenantId`; all access decisions go through
`server/src/lib/hubCore.ts` (`resolveCtx`, `canSee`, `canWriteRow`); marking,
mastery and spaced-repetition maths are **server-side only**; nothing about *what*
is taught is hardcoded (subjects/topics are tenant rows, kinds/bands/pass-marks are
`settings.hub`, see `lib/hubConfig.ts`); booking / invoicing / scheduling logic is
never touched; on/off = Setup → Features → "Learning Hub" (opt-in, default off).

## Access model (already built — milestone 1/2)

| Caller | Tenant | Scope |
| --- | --- | --- |
| company / freelancer / tenant-level staff | from token | whole tenant (all franchises) |
| franchise / franchise staff | from token | head-office rows read-only + own rows read/write |
| staff | from token | also gated by Roles & permissions area `learninghub` (View = read, Edit = author/mark) |
| parent | `?tenantId=` | ONLY via an **active `hubEnrolments` row** for their child; `?childId=` narrows to one child (must be theirs + enrolled) |

`resolveCtx(req,res)` returns `HubCtx {tenantId, uid, name, role, canEdit, franchiseId, children[], childId}` or has already sent 400/403/404.
Errors are `{error: string|issues[], code?}`. Feature off → `403 {code:"feature_off"}`. A foreign id is always **404**.

Prefer tenant-scoped single-equality reads filtered in memory otherwise.

## Rules (server-side)

**Marking** by `settings.hub.questionKinds[kind].mark`: `choice` all-or-nothing on option id; `multi` all-or-nothing on the option set; `exact` trim+lowercase+collapse-spaces vs `answer`/`acceptedAnswers`; `numeric` `|x−answer| ≤ tolerance`; `manual` → `correct:null`, attempt becomes `pending_marking` until a tutor marks it. `pct = round(Σawarded / Σmax × 100)` over questions counted so far; `passed = pct ≥ passMarkPct`.
**Reveal**: `correctAnswer`+`explanation` are stripped from anything a parent receives until `settings.hub.revealAnswers` allows (`after_pass` **(default)** | `after_submit` | `after_marked` | `never`). Answer keys are **never** sent inside a running attempt.
**Mastery** per (child, topic): take the last 5 *submitted, marked* per-topic slices with `max>0`, weight `0.5^i` (newest `i=0`): `Σw·(got/max)/Σw × 100`. Band = highest `settings.hub.masteryBands` entry with `min ≤ pct`. Subject rollup = mean of attempted topics + `coverage = attempted / published topics in subject`. Recompute after every submit and every mark.
**Diagnostic**: the first *marked* diagnostic for (child, subject) writes `baselinePct` per topic and is never overwritten (a tutor `reset-baseline` allows a retake). Diagnostic attempts **do not** count toward the mastery trend; quiz attempts count. If `settings.hub.requireDiagnostic`, starting a quiz in a subject without a diagnostic (or waiver) → `409 {code:"diagnostic_required"}`. `growth = mastery − baseline`.
**Spaced repetition (SM-2)**: client sends `quality` ∈ {1 Again, 3 Hard, 4 Good, 5 Easy}. `q<3` → `repetitions=0, interval=1`; else interval = `1` (reps 0) / `6` (reps 1) / `round(interval×EF)`, then `repetitions++`. `EF = max(srsMinEase, EF + 0.1 − (5−q)(0.08+(5−q)0.02))`. `nextDueAt = now + interval days`. Due queue = `nextDueAt ≤ now` plus never-reviewed (new) cards.
**Live lessons**: private Daily room per lesson via `POST https://api.daily.co/v1/rooms` (`DAILY_API_KEY`; see `server/src/lib/emails.ts ensureLeadVideoUrl` for the call style) with `privacy:"private"`, `exp` = end + 30 min; per-join meeting token via `POST /v1/meeting-tokens` (`is_owner` for the tutor, `user_name`, short `exp`). Join window: 10 min before start → 30 min after the end. Rooms are never public (minors).

## Questions, assessments, attempts, mastery — as built (milestones 3–5 ✅)

Code: `server/src/routes/hub/{questions,assessments,attempts,mastery}.ts` (mounted by `assessmentsApi.ts`, which also serves `GET /config`), pure maths in `server/src/lib/hubScoring.ts` + `hubMastery.ts` (self-test: `cd server && npx tsx src/hubSelfTest.ts`), API test `e2e/learning-hub-assessments.spec.ts`. Where this differs from the sketch above, **this section wins**:

- **Questions**: `published` defaults to `true`. An assessment can only be *published* when it has ≥1 question and every question is published, and every question must be in the assessment's `subject`; `topicIds` is extended with the questions' topics. A question used by a published assessment can't be deleted **or unpublished** (`409 {code:"question_in_use"}`); deleting one just removes it from draft assessments. Options may omit `id` (generated). A tutor's `GET /questions` also returns `usedBy` (assessment count).
- **Assessments**: `type` is immutable. Deleting is refused once attempts exist (`409 has_attempts` — unpublish instead) or homework (`hubHomework.assessmentId`) uses it (`409 in_use`). Parents get published-only summaries with **no** `questionIds`; `questionCount`/`totalMarks` count published questions.
- **Attempts**: `POST /assessments/:id/attempts` also returns `resumed` (an unfinished attempt is resumed; one past its time limit is discarded). The attempt stores a full `questions[]` snapshot (topic, marks, kind→rule, **key**) so edits to the bank never change how a running or past attempt is marked; that snapshot is never serialised to a family. Extra attempt fields: `subject`, `assessmentTitle`, `childName`, `late`, `baselineReset`. Submit/mark run in a transaction (double submit → `409 already_submitted`). A blank `manual` answer is worth 0 and does **not** wait for a tutor.
- **Scoring**: `maxMarks` = the whole assessment; `pct`/`byTopic` cover only questions *counted so far* (pending manual answers excluded); `passed` is `null` while `pending_marking`. `PUT /attempts/:id/mark` may also override an auto-marked answer; `correct` = full marks. `POST /attempts/:id/reset-baseline` sets `baselineReset:true` on that diagnostic.
- **Reveal**: `correctAnswer` (+ `acceptedAnswers`, `explanation`) reach a family only per `settings.hub.revealAnswers` and never while `in_progress`; tutors always get them. **Default changed (G2, 2026-09-20): `after_pass`** — the key opens only once THAT attempt reached the pass mark, or the child has already passed the quiz before. A marked-but-not-passed attempt returns `keyHeld:true` and no key/explanations (per-answer `correct` and marks still go out, so the child sees which were wrong). Why: with the old `after_submit` + unlimited retakes a child could re-sit a short quiz until they had read the whole key. A tutor who wants the old behaviour sets "Show right answers → Straight after they submit" in Setup → Learning Hub (or `PUT /config {hub:{revealAnswers:"after_submit"}}`); a tenant that had already saved its own value keeps it. A lesson's warm-up check has no pass mark and still reveals per question. Per-answer `correct`/marks are always returned.
- **Diagnostic gating**: `requireDiagnostic` only locks a subject's quizzes when a *published* diagnostic exists for it (else nobody could unlock them). Taking a diagnostic (any status but running) or a waiver lifts the lock. A diagnostic already taken and not reset is `409 diagnostic_done`. Waivers live on the enrolment doc (`diagnosticWaived[]`, lower-cased subjects): `POST /students/:childId/diagnostic-waive {subject, waived?:true}` → `{childId, waived[]}`. (Caveat: re-enrolling via `POST /students` rebuilds that doc and drops waivers.)
- **Mastery**: `GET /mastery` is computed fresh from the child's attempts (`hubMastery` rows are the derived copy — rebuilt after every submit/mark/reset, used by `/mastery/overview` and export). Only `status:"marked"` quiz attempts feed mastery and `trend` (oldest → newest, max 20); diagnostics only set the baseline (earliest marked, non-reset diagnostic per subject → per-topic `baselinePct`, once). A topic with a baseline but no quiz yet has `masteryPct:null, band:null, attempts:0`. Subject: `masteryPct` = mean of attempted topics, `coverage` = attempted ÷ topics that have published questions (0–1), `baselinePct` = mean of baselines, `growthPct` = mean of (mastery − baseline) over topics with both. Bands are looked up at read time from current settings.
- **Realtime**: `hubAttempts` channel — a parent streams only their own children's attempts, tenant-level operators the tenant's (pings only; no data). Questions/assessments/mastery are not streamed.

# Round 3 additions (owner feedback, 19 Sept) — THE CONTRACT for this round

Everything below is additive. Settings live in `lib/hubConfig.ts` (`HubSettings`: new `retakePolicy`, `retakeCooldownHours`, `yearGroups`).

## 1. Year group / age on assessments (placement tests AND quizzes)
- `hubAssessments.audience: { yearGroups: string[]; ageMin: number|null; ageMax: number|null }` — empty `yearGroups` and null ages = everyone. A tutor sets it in the builder (multi-select from `config.yearGroups` + optional age range). Tenant-configurable list, never hardcoded.
- `hubEnrolments.yearGroup: string|null` — the tutor tags the student (`POST/PUT /students {yearGroup}`); at enrolment it defaults from the child's `dob` with the UK rule (age on 31 Aug → Reception 4–5, Year 1 = 5–6 …; helper in `server/src/lib/hubCore.ts`, only when the tenant's `yearGroups` contains that label). Age is derived from `dob` (server-side, never stored on the assessment).
- Eligibility (server): if the assessment lists year groups the child's `yearGroup` must be one of them (case-insensitive); if it has an age range the child's age must fit; when the child's year/age is UNKNOWN the assessment is still shown but flagged `audienceUnknown:true` (never silently hidden). Parents see only eligible/unknown ones in `GET /assessments`; tutors see all with `audience` and `eligibleCount`. Starting an attempt for an ineligible child → `409 {code:"not_for_this_child"}`.
- API: assessment create/update bodies accept `audience`; list rows return `audience`; student rows add `audienceUnknown?`.

## 2. Images on questions
- Question: `image: {id, alt}|null` and per option `options[i].image?: {id}` (picture answers). Files are uploaded with the existing `POST /api/uploads {dataUrl, purpose:"private", kind:"hub"}` (tutor) and attached by id; the server verifies each id belongs to this tenant + kind hub (reuse `checkAttachments` logic; a question image can't be a homework/submission file). ≤1 image per question + ≤1 per option; PNG/JPEG/WebP/GIF, ≤750KB.
- Every payload that shows a question to a student (attempt start/resume, results review) returns `image: {url, alt}` and `options[].image: {url}` with SHORT-LIVED SIGNED URLS (lib/signing.ts signImageUrl), never bare ids. Answer keys stay hidden as before. Alt text is required when an image is set (accessibility).

## 3. Retake control (simple setting)
- `settings.hub.retakePolicy` (`unlimited|once|cooldown`) + `retakeCooldownHours`; an assessment may override with `retakePolicy: "inherit"|"unlimited"|"once"|"cooldown"` and `retakeCooldownHours`.

# Round 4 — whiteboard (live shared board for video lessons)

Code: client `features/learninghub/live/board/*` (self-contained; mounted as the **Board** tab of the in-call workspace by one line in `live/workspace/Workspace.tsx`), server `server/src/routes/hub/boardsApi.ts` (mounted from `teachingApi.ts`). Self-tests (plain TypeScript, no React/DOM/Daily — run from the repo root): `npx tsx features/learninghub/live/board/reducer.selftest.ts` (op reducer, permission gating, undo/redo, chunk/merge, size cap) and `npx tsx features/learninghub/live/board/sync.selftest.ts` (a fake Daily room: per-student permission enforced on every peer, late joiners, private pads never reach other students). API spec: `e2e/learning-hub-board.spec.ts`; UI spec: `e2e/learning-hub-board-ui.spec.ts` (two browsers in one Daily room).

**Data model.** A board is pages (`p1`, `p2`…) of vector **elements** (`stroke` · `shape` line/arrow/rect/ellipse/triangle · `text` · `sticky` · `image` · `stamp` number line/fraction bar/coordinate grid/times-table/clock/ruler/protractor). Every element has a random unique `id`, an owner (`own`: `"T"` tutor or `"c:<childId>"`), a stacking `z` and a version `v`. Edits are last-writer-wins on `v`; a delete leaves a tombstone; `clear` records the clear's version so a late-arriving older add is ignored — so replicas converge whatever the delivery order. Backgrounds per page: blank · lined · squared · graph axes (−10…10) · number line · isometric dots.

**Live sync (no server hop).** Over the Daily call: `callObject.sendAppMessage(msg, '*')` (< ~3.2 KB per message; ops are batched every ~40 ms, point streams merged, big strokes sliced). Ops: `add`, `pts` (append points while drawing, indexed by `from` so duplicates/gaps are detected and healed with a `need` resend), `upd`, `del`, `clear`, `bg`, `padd`/`pdel`/`pages`, `perm`, `reset`; ephemeral: laser/cursor `ptr`, `go` (tutor's page), `present`. `DailyFrame` publishes its call object through `board/callObject.ts` (`publishCall`) and that store buffers whiteboard messages from the moment the call exists, so opening the Board tab late replays what was missed. A joiner says `hello` and asks (`req`) for the board; the **tutor replies with the full state** (chunked), and re-sends it to everyone when the tutor rejoins.

**Wire hardening, identity, late join, resync (whiteboard sync round).** *Everything from the wire is untrusted*: `board/wireGuard.ts` sanitises every inbound message before the reducer/pad layer sees it — element fields are clipped/clamped to the SAME limits as the server's zod schema (text ≤ 2000, `own` ≤ 120, `cid` ≤ 100, ids ≤ 60, points finite ±1e6…), malformed ops are dropped, `need.have` is clamped and resends are rate-limited (a hostile `have: -1e12` can no longer hang the tutor), and a non-tutor peer is capped at ~800 ops/s. `PUT /lessons/:id/board` therefore **sanitises instead of rejecting** (repairs or drops bad elements and reports `dropped`; only "no usable page" is a 400), so one bad element can never stop autosave. *Identity*: a student's child id is NOT taken from `hello` any more — `POST /lessons/:id/join` mints a family token with `user_id: "c:<childId>"`, Daily signs it in and a client can't change it, and the board reads `participant.user_id` (`hello.cid` is ignored; a token without one has no child id and can only write under "everyone"). `present` is honoured only from an `owner` participant. *Late joiners / early link*: the Board tab is mounted as soon as the call starts (hidden), so the peer is introduced immediately; the tutor sends each newcomer (or anyone who `req`s) the board (with `perm`), then `present:true` if presenting and `go` to the tutor's page. A tutor who (re)joins broadcasts a **merge** (adds + `padd`/`bg`/`perm`, no `reset`), so a stale saved copy never wipes what students drew meanwhile; a student whose tutor reappears hands its own drawings back. *Resync*: on Daily `network-connection` "connected" a student re-sends its own work and `req`s a fresh copy (banner "Reconnecting…" meanwhile); the tutor sends a ~10 s fingerprint (`dg`) and a peer that differs twice running asks for a fresh copy. Messages are packed by UTF-8 **bytes** (CJK text), over-long text is shortened with a toast. The tutor's autosave uses `keepalive` when leaving (boards ≤ 60 KB). *Video tile*: it must never cover board controls — the controls carry `data-board-avoid`; the floating tile moves to the nearest free spot, or **docks** (beside the workspace on wide rooms, above it on phones / portrait) when none exists; "Dock/Float" lets the person choose. Self-tests: `sync.selftest.ts`, `wireGuard.selftest.ts`; UI spec `e2e/learning-hub-board-sync.spec.ts`.

**Who may write — enforced on the RECEIVING side.** The tutor is whoever holds Daily's `owner` flag (the meeting token from `POST /lessons/:id/join` has `is_owner` only for a tutor) — never anything in a message body. `perm = {all, ids[]}` (a tutor-only op, broadcast and kept in the snapshot): a student's ops are honoured only when `all` or their child id is in `ids`; an element added by a student is force-stamped with the sender's own key, name and childId; a student can edit/delete only their own elements; a student can never clear, change the background, add/remove pages, change permissions, or add images/stamps. Late or forged messages are ignored. Students draw in their own colour (from their name) with a name label on their cursor and fresh work; the laser pointer is the tutor's (and any allowed writer's).

**Student workings (private pads).** Each student also has a **private scratch page** ("My workings") that only they and the tutor see. Pad traffic is sent **targeted** (`sendAppMessage(msg, <session id>)` — student → the tutor's session, tutor → that student's session), never `'*'`; on receipt a student accepts pad messages only from the tutor and the tutor only from students. The tutor's **Student work** view shows a mini live board per student (~2 fps, only while on screen) with name, a "writing…" dot, time since their last stroke and a Done ✓; open one to enlarge it and mark over it in red; **Set a question** writes a text/picture question at the top of chosen students' pads; **Compare answers** enlarges the grid; **Show to class** copies a pad onto a new, read-only main-board page (tutor-owned) and **Send back** removes it; **Save all to notes** files one page per student as an *unpublished* note (private workings are never published to other families). Pads swap what only each side holds when either side (re)joins, so a refresh loses nothing. "Privacy: hide names" (workspace) masks names on tiles and pickers.

**Persistence.** `hubBoards/{lessonId}` `{tenantId, franchiseId, lessonId, pages:[{id, background, elements}], childIds (students who drew — for erase), updatedAt, updatedBy(+Name)}`; the tutor's client autosaves (debounced ~5 s, on tab-hide and on leave). Pads are not persisted (they live in the call; the tutor's "Save all to notes" is the record).
- `GET /api/learning-hub/lessons/:id/board` — a tutor who can see the lesson's students, or a family whose enrolled child is in it (`?tenantId=&childId=`; `readOnly:true`). Nothing saved → one empty page. Image elements get a fresh signed `url` (6 h).
- `PUT /api/learning-hub/lessons/:id/board {pages}` — tutor only (franchise: own lessons). zod-validated; body ≤ 700 KB (`413 board_too_large` with a friendly message — the client first simplifies long strokes to fit); images must be this tenant's private `kind:"hub"` uploads (references only, never inline bytes); `cid`s not in the lesson are dropped. Foreign / unknown lesson ids are 404 for everyone; a parent PUT is 403.
- The board is deleted with its lesson (`DELETE /lessons/:id`), listed in `e2eCleanup` (`hubBoards`) and student-authored elements are removed when the parent deletes the child (`eraseChildLearning`). Not added to the privacy *export* (drawings carry no data beyond the first name + a stroke).

**Export.** "Save to lesson notes" renders the page (or every page) to a PNG (JPEG fallback) ≤ 750 KB → `POST /api/uploads {kind:"hub", purpose:"private"}` → `POST /api/learning-hub/notes` titled `Board — <lesson> · <date>` (filed under the lesson's topic, else the tutor's first topic) → `PUT /lessons/:id {noteIds:[…, new]}`, so families revisit it from the lesson. "Download PNG" is client-only.

**UI.** Tools: select/move, pen (9 token colours + custom, 4 sizes, pressure-aware), highlighter, eraser (whole-drawing, 4 sizes), text (sizes, bold), sticky notes, shapes (Shift or hold = straight/square/15° snap), laser pointer, pan; teaching aids (number line with min/max/step, fraction bars ½…1/12 with click-to-shade, coordinate grid, times-table grid, clock with editable time, ruler, protractor — the last two rotatable); pictures (upload with browser-side shrink, or from the tutor's notes); pinch/wheel/space-drag pan-zoom; multi-page; per-user undo/redo; keyboard: V P H E T S L A R O G Q M, Ctrl+Z / Ctrl+Shift+Z, Delete, Ctrl+D, +/−/0. **Present** puts the board on the main stage (the call room's "workspace only" layout: the video becomes a small floating tile) and tells students' rooms to do the same. Phones: the tool tray runs along the bottom, the board fills the screen.

## Scale — a fully seeded provider (as built)

A provider seeded with the curriculum packs holds ~700 topic rows, ~5,000 questions, ~450 quizzes + ~70 placement papers,
~450 notes and ~4,500 flashcards. The hub was designed for tens of items; these are the rules that keep it fast at that size
(measured with `server/src/hubLoadTest.ts` — `setup | seed | bench <label> | compare a b | clean`, its own scratch tenant).

**Server**
- **Read models, not collection scans.** `lib/hubIndex.ts` keeps short-lived per-tenant caches (`lib/hubCache.ts`, single-flight):
  the topic tree (60 s), a LIGHT question index (id/topic/kind/prompt/marks/published/image flag — never the key, options or
  explanation), the note index (excerpt, read time, attachment meta, lower-cased text for search), the assessment rows, a light
  flashcard index and the roster (30 s). Every API write patches the cached copy in place (`patchQuestion`, `patchNote`,
  `patchAssessment`, `patchCard`, `patchTopic`) or drops it (`forgetHub`), so a tutor sees their own change at once; the TTLs
  (3 min for the big indexes) are only the backstop for writes that bypass the API (seed scripts). **Access is never cached** —
  callers filter the cached tenant-wide rows through `canSee` / `subjectAllowed` on every request.
- `resolveCtx`: a parent's active enrolments are cached 8 s (`forgetEnrolments()` on every roster write and the privacy erase, so
  pausing a child cuts access immediately); child dates of birth 2 min.
- **Lists are light and pageable** (additive query params; old shapes still work): `GET /notes` (no bodies; `?full=1` = old shape;
  `GET /notes/:id`, `GET /notes/counts`), `GET /questions` (`light`, `topicId(s)`, `subject`, `q`, `kind`, `published`, `sort`,
  `limit/cursor`; `GET /questions/:id`, `GET /questions/counts`; an un-paged call is capped at 200), `GET /assessments`
  (`light`, `yearGroup`, `published`, `q`, `limit/cursor` + `facets`; `GET /assessments/:id`; question count / total marks come from
  the light index, never from question documents), `GET /flashcards` (`subject`, `q`, `published`, `sort`, `limit/cursor`; capped at
  500 un-paged). `/flashcards/due` reads the light card index + the child's review rows and only the ≤50 handed-over cards in full.
  With `limit`/`cursor` the reply is `{items, total, nextCursor}`; without them it is the array it always was.
- `GET /mastery` no longer reads every question (uses the light index); `recomputeChildMastery` uses the cached topic tree;
  `/mastery/overview` reads a 20 s field-masked copy of the mastery rows. Attempt start issues its independent reads together.
- Topic cap raised 400 → 2,000 (renames/deletes are chunked); flashcard cap 3,000 → 20,000.
- **gzip** on every hub JSON response over 1 KB (`lib/gzipJson.ts`; the API had no compression). `GET /topics` and `/notes/counts`
  send `Cache-Control: private, no-cache` + the automatic ETag so the browser revalidates instead of re-downloading.
- **Realtime (`routes/events.ts`)**: attaching a Firestore listener reads the whole result set, so the big collections are no longer
  streamed. `hubTopics / hubNotes / hubQuestions / hubAssessments / hubFlashcards / hubAttempts` are PING channels: each API write
  stamps one tiny per-tenant doc (`hubPings/{tenantId}`, `lib/hubPing.ts`, coalesced to ≤1 write / 0.7 s) and the stream listens to
  that single doc. A change made by a seed script (bypassing the API) doesn't ping; the small collections (homework, lessons,
  submissions, groups, enrolments) keep real listeners.
- No new composite indexes are needed: every new query is equality / `in` on `tenantId` + `topicId`, sorted in memory.

**Client (`features/learninghub/`)**
- The shell fetches topics + roster + config for first paint; note counts (sidebar badges, hero) come from `/notes/counts` and the
  tutor's groups arrive after — neither blocks a tab. The Notes panel fetches its own light, server-searched, 40-at-a-time list
  (sorted by topic) only once it is shown, and a note's body only when it is opened.
- Question bank: server-filtered by the sidebar's topic/subject + a debounced search, light rows, "Show more". The assessment
  builder's picker is scoped to the chosen topics (else the subject), searched server-side, 30 at a time — it never holds the bank.
- Quizzes / placement lists: light rows; more than 36 papers become collapsed subject → topic groups with "Show more"; year-group
  chips carry counts. A family's list shows subject chips with counts and 24 cards at a time.
- Tutor flashcards: scoped to the sidebar selection, 60 at a time, server-side search.

# Lessons — the interactive lesson player (UI name for hub "notes")

The hub tab "Notes & resources" is now **Lessons** (tab key, `hubNotes` collection and `/api/learning-hub/notes` paths are unchanged; **Live lessons** stays its own tab). A lesson is either a plain markdown note (unchanged) or a note that carries the structured **`lesson`** field (Oak import, docs/oak-import.md) — those render as a step-by-step interactive lesson.

Code: `features/learninghub/lesson/` — `LessonPlayer.tsx` (Start → Learn → Key words → Warm-up → Quiz → Done, sticky header with progress / XP / streak, confetti, OGL credit) with `LearnStep · WordsStep · WarmupStep · QuizStep · DoneStep · KeywordText · Attribution`, and `LessonTutorPanel.tsx` (tutor view). `NotesPanel.tsx` opens the player for pupils; for tutors the reader shows the tutor panel with **Preview lesson** (player, read-only — nothing started or saved) and the **widget picker**. Server: `routes/learningHub.ts` (notes carry `lesson`), `routes/hub/lessonApi.ts` (warm-up questions). Spec: `e2e/learning-hub-lessons.spec.ts` (fixture builder `e2e/helpers/lessonFixture.ts`).

**`lesson` field as the player reads it** (`lesson/types.ts normalizeLesson` accepts both spellings): `subject, keyStage, year, unit, outcome`, `steps` (or `points`: the key learning points, strings or `{text}`), `outline[]`, `keywords[{keyword,description}]` (or `{k,d}`), `plan` (the step-by-step lesson plan, `lesson/plan.ts`; replaces the old raw `transcript[]`, which is no longer written or shown), `warmupQuestionIds[]`, `quizId`, `widget` (id or null), `source{provider:"oak",url,licence,attribution,programmes,fetchedAt}`; tutor-only `misconceptions[{misconception,response}]`, `teacherTips[]` (the API strips both from a family's `GET /notes/:id`, and strips `plan.commonMistakes` / `plan.watchOut`; the plan steps stay: they are the child's "Recap: step by step"). An Oak lesson MUST show the OGL credit — `Attribution.tsx` does, from `source`.

**Real vs practice.** The **exit quiz** (`lesson.quizId`) is a REAL attempt (`POST /assessments/:id/attempts` → `POST /attempts/:id/submit`): marked server-side, rolled into mastery, retake / audience rules apply; answers stay in the browser until the last question is handed in; match/order use `shared-assess/QuestionView`. The **warm-up** (`lesson.warmupQuestionIds`, ordinary `hubQuestions`, an optional stored `hint` string) is instant-feedback practice — nothing is stored, nothing feeds mastery. XP / streak / stars are cosmetic (session state).

**API additions.**
- `GET /notes/:id` now returns `lesson` (teacher-only parts dropped for families); list rows add `isLesson`, `lessonWidget`. `POST /notes` accepts `lesson` (`warmupQuestionIds` / `quizId` must be this tenant's); `PUT /notes/:id` **keeps** the stored lesson when `lesson` is omitted (the markdown editor never sends it), `lesson:null` turns it back into a plain note.
- `PATCH /notes/:id {lesson:{widget: string|null}}` (tutor) — attach / detach the Explore widget (id shape `^[A-Za-z0-9_-]{1,40}$`; 409 `not_a_lesson` on a plain note). The registry of widgets lives in the web app.
- `GET /notes/:id/lesson-questions[?childId=]` → `{warmup: TakeQuestion[] (+hint), quiz:{id,title,questionCount}|null}` — no answer keys (match/order pieces shuffled like an attempt).
- `POST /notes/:id/warmup-check[?childId=] {questionId, response}` → `{correct, pending, marksAwarded, marksMax, correctAnswer?, explanation?}` — marks with `lib/hubScoring.markResponse`; the key/explanation is revealed for THAT question only, and only when `settings.hub.revealAnswers` allows (tutors always). A pupil can therefore probe a warm-up question by trying answers — accepted for low-stakes practice.

**Explore widgets** (`lesson/widgets/`). `index.ts` is the typed registry `id → {title, intro, Component}` (`WIDGETS`, `getWidget`, `listWidgets`, `suggestWidget` from the prototype's `rules.json`). Native React widgets: `fractionBar`, `neurone`. Every plain-JS widget in `scratch/prototype/widgets/**/*.js` (`WIDGETS.id = {title, intro, html(), init()}` using `$ esc md shuffle addXP gcd`) is mounted by the generic `<LegacyWidget>` adapter — **run `npm run hub:widgets` after adding or changing one** (`scripts/hub-widgets.mjs` generates `lesson/widgets/legacy/*.gen.ts` + `manifest.gen.ts` + `rules.gen.json`; it also runs before `npm run build`; the generated files are committed so a build without `scratch/` still works). `$` is scoped to the mounted widget and `addXP` feeds the player's XP pill; the wrapper maps the prototype's colour names/classes onto the hub tokens.

# In-person lessons — "Teach in person" (a lesson with the children beside the tutor, no video)

Owner requirement: run a lesson when the children are physically with the tutor. The tutor runs the lesson (the slide player) on THEIR device and taps in each child's answers; every child gets a REAL, marked attempt their parent sees. The children have no login; nothing here needs one.

**Model.** A session is an ordinary `hubLessons` row with `mode:"in_person"` (`status` `live` → `ended`, no room, `startsAt` = now). It is hidden from `GET /lessons` and refused by `join / extend / reopen / edit` (those answer 404), so the video views never show it — but attendance, the privacy export/erase and the `hubLessons` realtime channel already cover it. `attendance{childId: iso}` is **tutor-settable** here (for video lessons only a family joining sets it). A result is an ordinary `hubAttempts` doc with two additive fields, `mode:"in_person"` and `sessionId`; every attempt list/result row now carries `inPerson: boolean`. Old attempts/lessons have neither field and behave as before.

**API** (all tutor-only; see `server/openapi.yaml`, code in `server/src/routes/hub/inPersonApi.ts`):
- `POST /in-person/sessions {childIds[]?, groupIds[]?, noteId?, assessmentId?, title?, key?}` → session (attendance = everyone chosen; `key` makes a retry return the same session). Every child must be an ACTIVE enrolment of this tenant inside the caller's scope, else 404.
- `GET /in-person/sessions[?status=live]`, `GET /in-person/sessions/:id` (+ `results`), `PUT …/attendance {present:{childId:bool}, add?:[childId]}`, `POST …/end {warmup?}`.
- `GET …/questions[?assessmentId=]` → the paper as ONE class sees it: a session-seeded shuffle for match / order (a projected screen matches every child) + the tutor's `key` per question.
- `POST …/submit {assessmentId, children:[{childId, answers:[{questionId, response?, verdict?}]}], override?, linkHomework?}` → per child: snapshot, server-side marking, a stored attempt, mastery recompute, attendance, notification. `verdict` = the tutor's own right/wrong call for oral work. Idempotent (attempt id = hash of session+quiz+child). Gates: a child outside the session / roster / tenant is `skipped` and never recorded; `retake_blocked`, `diagnostic_required`, `not_for_this_child` skip the child unless the tutor sends `override:true` ("Allow anyway" in the UI); `diagnostic_done` is never overridden (reset the baseline). Open homework for the quiz is handed in with the attempt (`linkHomework`, default on).
- Notifications: one bell/email per child ("Lesson done with your tutor", their score, category `learning`) when their result is recorded; on `end`, children who were here but had no quiz get "completed the lesson … in person". Parents' `GET /attempts` rows include `inPerson:true`.

**UI** (`features/learninghub/inperson/`, all new files; entry points are tiny edits): `TeachInPersonButton` (Lessons list top bar, an open lesson's toolbar pre-selects it, Live lessons header) and a Home quick-action tile all open `InPersonApp` — a full-screen layer (via `FullscreenPortal`) with: `SetupStep` (an interactive lesson, or a quiz / placement test alone; groups + roster search; "Resume" for a still-open session) → the real `LessonPlayer` in read-only mode with `inPerson` slots (`LessonPlayer.tsx`: banner, quiz, warmupExtra, done) → `WarmupExtra` (show the answer + per-child got-it/not-yet taps, kept on the session, never mastery) → `CaptureGrid` (one question for the class; a row per present child: their option, typed answer, or the tutor's ✓/✗; "Everyone got it", tutor-only "Show answer") → `ResultsPanel` (child × question ✓/✗, score, under-pass-mark chip, attendance toggles, "Allow anyway" for a skipped child, follow-up homework via `setHubIntent` → HomeworkForm pre-filled, Finish). Captured taps persist in `localStorage["hubclass:<sessionId>"]`, so a refresh resumes; "Hide names" shows initials for a projected screen. Portals: freelancer / company / franchise / staff (server `requireEdit`; view-only staff get the server's 403).

**Not built (known gaps).** Warm-up answers are class-level oral practice (tallies on the session), NOT attempts — a warm-up is not an assessment, so nothing feeds mastery; only the quiz does. Flashcard review in person is not covered. There is no per-child "turn-taking" mode (the capture grid is the one path). A parent-side "In class" badge is API-only (`inPerson`), not yet drawn.

## Family hats: parent + child on the parent's device (`features/learninghub/family/`)

- **Which child?** `FamilyContext` (`useFamily`, `ChildChip`, `WhoIsLearning`). Every runner (quiz, lesson + its exit quiz, flashcard review, homework) shows the child's chip and looks the name up from the SAME child id it posts results with. With 2+ children, Start stays off until somebody has said who is learning (a tap in the hero picker, a link carrying `child=`, or a remembered pick); intro screens carry "Ava is doing this. Not Ava? Switch".
- **Kid mode** ("Hand over to Ava", `KidMode.tsx`, `ParentGate.tsx`): the hub root goes `fixed inset-0` over the portal chrome, scoped to one child, tabs limited to Home / Lessons / Quizzes / **Starting quiz** (the placement test, so a quiz locked behind one can be unlocked from kid mode: a locked card has a "Go to the starting quiz" button; same runner, child chip and forced child, and no sibling switch) / Homework / Flashcards, child-friendly wording (no "mastery", "attainment", "placement", "baseline", "diagnostic"; the default level names Learning / Developing / Secure read "Getting started / Getting there / Got it!" — a tutor's own names are untouched; `kidBand` in `family/KidMode.tsx`), Back kept inside the hub. Persisted in `sessionStorage` (`aos.hub.kid`). Exit = a small sum (`kid-gate-sum`).
- **Deep links** (`link.ts`): `?tab=&child=&open=quiz|lesson|hw:<id>[&hw=<homeworkId>]`. Opening pushes a history entry; Back (or the runner's own X) closes it. A refresh mid-lesson resumes the step (`sessionStorage hublesson:<child>:<note>`), a quiz resumes from the local draft. A homework's "Take the quiz" / "Start the lesson" use these links and the attempt is started with `homeworkId`.
- Exit quizzes of lessons are flagged `lessonNoteId` on `GET /assessments` (family rows): listed under "Finish a lesson to unlock", never as Home's "Up next".
- Parents also get a "this week" summary on Home and "Ask your tutor" (→ `/custdash/messages?compose=1&tenant=<id>`).

## Siblings in one live lesson (G2)
`POST /lessons/:id/attended` and `POST /lessons/:id/join` accept `childIds:[a,b]` (a parent's OWN children who are in the lesson; others ignored). `attended` records every named child present in one write (reply `{ok, childIds}`); `join` mints ONE token named "Ava and Ben" (whiteboard identity stays `c:<first child>`) and returns `childIds`. Client wiring (a "Ben is here too" choice in the family Lobby, then sending `childIds` on join + attended) is in the live-room files, not done in this pass.

## Ready-made homework per lesson (2026-09-21)
Every lesson (an imported Oak lesson or any note) can hand a tutor a complete suggested homework without storing anything: `GET /api/learning-hub/notes/:id/homework-pack` (tutors) runs the pure function `server/src/lib/hubHomeworkPack.ts` over the lesson's own data — title "Homework: <lesson>", instructions (the lesson's outcome; revise its key learning points + key words; do its exit quiz; review its N flashcards; hand in), `assessmentId` = `lesson.quizId`, `noteIds:[lesson]`, `flashcardTopicId` (the lesson's topic, only when cards with `lessonId == lesson` exist), `dueInDays` (settings.hub.homeworkDueDays, default 7), `year` (the lesson's year, for "everyone in Year N"). Only the lesson's own words are used (templates around them). UI: the lesson reader's "Set for children" and the Homework tab's "Set homework" open `HomeworkForm` (`homework/HomeworkForm.tsx`, `homework/hwPack.tsx`) prefilled from the pack — everything editable, the tutor picks children and presses Assign; a "Base it on a lesson…" search fills the fields from any lesson; when the lesson has a year a "Set for all my Year N students" button ticks the matching roster (groups already have their own quick pick). `POST /homework` is unchanged, so families get the same notification and see it in My Classroom.
